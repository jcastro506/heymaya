## BLUEPRINT
Maya is an app-distribution agent with one job: get the user customers for their app and prove it. The ideal product is a tight loop with four load-bearing pillars that the current code only half-implements. PILLAR 1 — VOICE: at onboarding, for EVERY user with handles (mode-independent, not manager-gated), Maya pulls their own accounts via ScrapeCreators, WATCHES their videos multimodally (review_media), READS their text, and persists a real voice fingerprint (gtmAgents.voiceProfileJson) that renders into USER.md and anchors every later draft. PILLAR 2 — EQUAL SIX-CHANNEL RESEARCH: TikTok / Instagram / Reddit / YouTube / X / LinkedIn are first-class and equal-depth. YouTube is un-excised end-to-end (judge, picker, deploy roster, SKILLS bundle, save-tool enums); Instagram gets a real researcher skill; the Reddit/HN lean is de-biased in prompts. For each bet channel, the WHERE-they-live + what-they-watch/complain/talk + native-style exemplars persist as structured per-channel ICP knowledge (gtmChannelScorecard.icpKnowledge + styleExemplarsJson). PILLAR 3 — ONBOARDING ENDS AT DAY-1, NOT A WEEK: onboarding's terminal output is voice-built + research-saved + ONE turn-key first move for today. The hard completion gate flips from "non-empty full week" to "voice profile + foundation rows + exactly one day-1 event." No rolling 7-day plan, no "first week" promises. PILLAR 4 — THE MORNING CRON OWNS ALL PLANNING: every 7am, Maya reads the STORED ICP knowledge (get_my_foundation) and per-channel WARMTH (channelWarmthJson), intersects it with what's live on the channels that day, and emits TODAY's turn-key calendar events (one-tap openUrl + verbatim draftText, server-validated). Warmup is generalized to all six channels and advanced over time via set_channel_warmth — cold channels get warmup_block-only, warm channels go straight to posting in the user's voice. Anti-slop is enforced not just in prose but with a deterministic backstop: drafts can't reach the calendar without a recorded voiceMatchScore>=0.7 and slopCriticPassed, and the outbound firewall gains a structural-AI-tell + voice-divergence LLM pass.

The resolved product tension is immediate-value vs no-week: onboarding still delivers a "wow" (the cited ICP read + their voice captured + one concrete move they can do today), but the week is gone — the daily cron is where planning lives, grounded in stored knowledge + live state. Messaging is minimal by hard budget: ~2 proactive Telegram sends/day steady-state (morning brief + conditional evening recap), onboarding budget is exactly 2 (hello + synthesis), and ALL internal progress/play-by-play routes to the web Mission Control view via post_activity, never the phone. The ideal Maya reads as a native member of every community the user posts in, sounds like the user themselves, references stored ICP intelligence every single morning so the research pays off daily instead of decaying after onboarding, and touches the user's phone only with high-value, act-on-it moves.

## IDEAL CRON DESIGN
LOCKED CRON SET for the solo indie/AI-native builder with a day job (maximally useful, low-noise). All self-scheduled by Maya at BOOT step 4 once foundation_completed_at exists; jobs.json ships only the one-shot 0001_kickstart hello.

KEPT:
- morning_brief — 0 7 * * * (daily). The ONE turn-key daily plan. Now MUST first call get_my_foundation (stored ICP buyer map + per-channel icpKnowledge) and read channelWarmthJson, then intersect stored knowledge with live channel state to build TODAY's events. Emits 1 Telegram. This is the planning owner — there is no onboarding week and no populator-owned "rolling week."
- midday_pulse — 0 13 * * * (daily). Light fresh-only velocity re-sweep that ADDs (never replaces). SILENT by default — only pings Telegram if something genuinely clears T1. Reaffirm silent default in copy. Catches the pre-evening-peak window for the ICP.
- weekly_review — 0 19 * * 0 (Sun 7pm). Strategic 4-block message. RE-SCOPED: it re-weights bet channels by what converted and advances warmth (set_channel_warmth), but it does NOT regenerate a "next-week rolling plan" — the daily cron owns day-to-day. 1 Telegram/week.
- monthly_reset — 0 6 1 * * (1st, 6am). Re-runs foundation research AND re-ingests the founder's newest posts to refresh voiceProfileJson + per-channel styleExemplars. Now SILENT-on-progress: no replay of onboarding progress pings; at most ONE Telegram only if the month-over-month diff is operator-worthy (channel changed, new buyer pocket).

CHANGED:
- evening_recap — 0 20 * * * but now CONDITIONAL, not unconditional. Skip-when-empty: on a genuinely empty day (0 events existed AND 0 actions AND no attribution movement) fold the one honest line into tomorrow's brief instead of sending. EXCEPTION preserved: if events WERE planned and NONE got done, still send the one-line accountability flag (the launch-killing-silence catch). Fires only when there's something real to close the loop on.

CUT/FOLDED:
- The old deploy-time gtm_weekly_review / gtm_channel_discovery crons stay removed (already done).
- Discovery is crons-only (morning_brief + midday_pulse). The heartbeat NEVER discovers — it only monitors and fires gated, batched, capped go-time reminders (top ~2-3 events/day, batched per window, never re-remind an acted-on event) and self-heals stuck workers SILENTLY (no operator ping).
- No "calendar_build" research phase as a planning step — onboarding's terminal phase is strategy/voice-saved + single first move, not a week build.

Steady-state operator phone budget: ~2 proactive sends/day (brief + conditional recap), exceptions only (hot midday thread, 5x post, unanswered inbound, capped go-time reminder). Onboarding budget: 2 (hello + synthesis). Everything else → post_activity web view.

## RISKS
- Schema-ceiling hard constraint: the repo is at the 138-table TypeScript DataModel instantiation ceiling (note at schema.ts:4717-4720 — a 139th table regresses db.get() narrowing project-wide). EVERY new data structure here MUST be a JSON-string field on an existing row (voiceProfileJson, channelWarmthJson, icpKnowledge, styleExemplarsJson) — verify no implementer adds a table.
- Generators.ts is the single highest-risk file: ~22 edits across 5 dimensions in one ~1500-line file. Edits can conflict (e.g. the no-week BOOT gate vs the messaging cron-doc block sit near each other). Must be a single serial pass with re-Read between edits; parallelizing edits to this file will collide.
- Prose-vs-enforcement gap is the historical failure class in this codebase (foundation data that was 'described but never saved'). The plan adds typed save tools (save_voice_profile, save_style_exemplars, set_channel_warmth) AND deterministic backstops (turn-key calendar validation, approval voice/slop gate) precisely because skill prose alone has empirically not landed data — do NOT drop the typed-tool + server-guard half in favor of prose-only.
- The approval voice/slop gate (voiceMatchScore>=0.7 AND slopCriticPassed) is fail-closed: if voiceMatchScore is null because no voice profile was built (e.g. user with zero handles, confidence:'none'), drafts could be permanently blocked. The gate must treat 'no profile / confidence:none' as a pass-with-warning path, not a hard block, or low-signal users can never publish.
- YouTube re-enablement touches 6+ surfaces (judge, scoring, picker, deploy roster, SKILLS bundle, 3 save-tool enums). Miss any one (e.g. the record_published enum still bans youtube) and a youtube bet is scored but unpersistable — partial enablement is worse than none. The save-tool enum changes in index.js + the bundle regen are the easy-to-miss pieces.
- calendar_build research-phase rename (researchLifecycle.ts:56) risks breaking dependents that key off the enum literal. Keep the enum value stable if anything asserts on it; only change the meaning/usage. Grep for 'calendar_build' across convex/ before renaming.
- Turn-key server validation (reject events lacking openUrl+draftText for launch/reply kinds) could block legitimate warmup_block / engagement_block events that intentionally have no product link. Scope the validation strictly to {reply_window, soft_launch_post, hard_launch_anchor} and exempt warmup/engagement kinds, or warmup-phase days will fail to schedule.
- Onboarding voice pull adds latency to the already 10-15min foundation pass (pulling + multimodally watching the user's own videos). For users with many handles this could push the pass long; ensure Phase 0 is bounded (last ~20 posts / top videos only) and that the long-pass never-silent floor is the ONE allowed Telegram line, not a regression to progress-spam.
- Per-channel warmth onboarding UI must stay sub-4-min: showing a warmth dropdown for every connected channel risks form-bloat. Mitigation in the plan is to pre-fill from the ScrapeCreators pull and only show channels the user connected — verify the UI doesn't become a multi-step form (violates the conversational-onboarding principle).
- Bundle regen (bundledLocalSkills.ts) and tsc MUST be the last steps and MUST pass clean (convex tsc 0, root tsc 0) before any live deploy — the operator's standing rule is validation = real deploy + DM, not just assertion tests, so a live smoke after merge is required to confirm the typed tools land data (the recurring empty-DB failure).
