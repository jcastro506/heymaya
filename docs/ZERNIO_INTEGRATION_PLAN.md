# Zernio Integration — GTM Sprint Plan (architect synthesis, 2026-06-02)
> Research: 6 agents over the live Zernio docs (docs.zernio.com), pricing, our existing convex/integrations/zernio scaffold, + reviews. Full findings appended.

## Vision
Zernio collapses Maya's biggest gap: today she researches where buyers are, drafts in the founder's voice, and hands over one-tap deep links the founder pastes manually — because auto-post was app-approval-gated per platform. Zernio holds the platform app-approvals itself, so a single app-level ZERNIO_API_KEY + per-founder OAuth connections turns Maya into a real "we post for you" agent across X, Reddit, LinkedIn, IG, TikTok, YouTube, Threads, FB, Pinterest, Bluesky — bypassing the multi-week TikTok/IG/YouTube review walls that forced the paste-calendar. That flips the locked $99 "Maya makes + posts the content" promise from aspiration to mechanism, and the gtmCalendarEvent recipe becomes a Zernio payload instead of a copy-paste card.

The deeper leap is that Maya stops being a fire-and-forget link generator and becomes a closed-loop, real-time agent with a comprehensive view of the founder. Reads (GET /v1/analytics + follower-stats) give her the founder's ACTUAL post performance — impressions/reach/engagement on real posts, including externally-synced manual ones — finally grounding "what converted" beyond our wrapped-link clicks (attribution moat #2). Webhooks (post.published, comment.received, message.received, mention, account.disconnected) make her event-driven: she starts tracking a post the moment it publishes, drafts voice-matched replies to comments/DMs as they arrive, and proactively nudges a reconnect before "we post for you" silently breaks. Three pillars — posts + reads + monitors — off one OAuth connection, interface-isolated so Zernio stays swappable.

## New features
### Maya auto-posts the calendar across all channels ("we post for you")
- The gtmCalendarEvent recipe (WHAT/LINK/VOICE NOTES) is rendered into a Zernio POST /v1/posts payload and published on schedule, with per-platform copy overrides and firstComment used for links (avoids LinkedIn's 40-50% link-reach penalty). Channels are gated: true auto-post for low-ban-risk surfaces (X, LinkedIn, Threads, Pinterest, FB Pages, Bluesky) first; Reddit and TikTok stay draft/deep-link by default (ban-safety + TikTok consent flags) with explicit per-post user confirmation before going auto. Every publish is followed by a 24h re-poll to confirm it actually landed (silent-failure mitigation).
- **Powered by:** POST /v1/posts (publishNow/scheduledFor/draft, multi-platform, customContent, firstComment, threadItems) + POST /v1/media/presign for media-required platforms
- **Value:** Delivers the locked $99 Pro tier differentiator and removes the exact blocker that made us ship the manual paste calendar. The deep-link-and-paste friction is the #1 thing standing between Maya and "done for you."
### Real-account attribution (closes the loop beyond wrapped-link clicks)
- Maya reads per-post impressions/reach/likes/comments/shares/saves/clicks/engagementRate on the founder's actual posts (incl. source=external manual posts) and follower growth time-series, joins them to gtmAttribution/gtmPostResults, and reports which CHANNEL and which POST FORMAT drove reach + signups — not just which wrapped link got clicked. Wrapped links stay the low-latency same-day signal; Zernio analytics are the slower (60min-48h) ground-truth confirmation.
- **Powered by:** GET /v1/analytics (per-post + list, source=all), GET /v1/accounts/follower-stats, GET /v1/analytics/instagram|youtube/demographics
- **Value:** Hardens attribution moat #2 ("proves what converted") with real platform performance, and powers a far richer founder God-view. This is the data that justifies retention.
### Data-grounded scheduling (best-time + cadence)
- Maya upgrades calendar timing from heuristic cadence to data-grounded optimal posting windows per platform, and respects per-platform velocity limits in her cadence engine.
- **Powered by:** GET /v1/analytics/best-time, /posting-frequency, /content-decay, /daily-metrics
- **Value:** Turns scheduling from a guess into a grounded recommendation — directly on-brand with the "grounded or silent" principle.
### Real-time comment & DM triage (Maya watches, drafts replies)
- comment.received / message.received / mention webhooks wake the agent with the comment/DM + post context; Maya runs the voice-matcher, drafts a reply through the existing /lc_gtm/drafted_content approval pipeline, and surfaces it on Telegram as a one-tap card. lead.received (Meta Lead Gen) routes straight into the signup-attribution funnel. IG conversation participant followerCount/isVerified gives lead-qualification. Drafts-not-autonomous-send by default (reply endpoints exist for a future one-tap send).
- **Powered by:** Webhooks comment.received/message.received/mention/lead.received + GET /v1/inbox/comments, /v1/inbox/conversations, POST reply endpoints
- **Value:** Converts Maya from fire-and-forget into a real-time agent who catches the launch-post reply or "how does your app work?" DM the founder would otherwise miss — push-don't-pull, high perceived value.
### Reconnect-health guardian (anti-silent-failure)
- account.disconnected fires on token expiry/revoke; Maya proactively DMs the founder "reconnect your TikTok so I can keep posting" with the re-connect deep link. A Settings panel driven by /v1/accounts/health shows per-channel healthy/warning/needs-reconnect.
- **Powered by:** Webhook account.disconnected + GET /v1/accounts/health
- **Value:** Protects the entire "we post for you" promise from silently breaking — an anti-churn signal that directly defends the headline feature.

## Integration architecture
REUSE the existing scaffold in convex/integrations/zernio/ — but interface-isolated per its own contract. (1) client.ts is reusable AS-IS: ZernioClient (Bearer auth, 3-attempt jitter backoff, Retry-After/429 handling, never-retry-4xx), the typed error hierarchy (ZernioAuthError/RateLimitError/PlatformError/ApiError/TimeoutError), and verifyZernioSignature (constant-time HMAC-SHA256, accepts bare or sha256=-prefixed). FIRST FIX: re-point DEFAULT_BASE_URL from https://getlate.dev to https://zernio.com/api/v1 and the signature header constant from x-late-signature to x-zernio-signature (keep x-late-* as legacy alias), then live-smoke it — every path is marked [unverified] and was never tested. (2) endpoints.ts WRITE wrappers (multiPlatformPost -> POST /v1/posts) are reusable with minor edits: re-verify payload shapes, expand the ZernioPlatform union from 8 to the 15 GTM cares about (add reddit/youtube/bluesky/etc.), add the missing presign upload helper and the NOT-YET-BUILT read wrappers (getPostAnalytics -> GET /v1/analytics, getFollowerStats -> GET /v1/accounts/follower-stats, listInboxComments, listConversations).

THE KEY ARCHITECTURAL DIFFERENCE FROM THE SERVICE SCAFFOLD: the deployed GTM agent reaches Convex via OpenClaw TYPED PLUGIN TOOLS (infra/openclaw-runtime/plugins/maya-gtm-tools/index.js -> /lc_gtm/* HTTP endpoints in convex/http.ts), NOT Convex action()s. So the service-product oauth.ts (Convex actions) and webhooks.ts (businesses-keyed) are NOT reused for the agent path — instead:

NEW PLUGIN TOOLS (added to maya-gtm-tools/index.js, following the existing postJson/getJson helper pattern): post_to_channel (write), get_account_analytics + get_follower_stats (read), list_inbox / list_inbox_comments / list_conversations (monitor), reply_to_comment / send_dm (respond), list_connected_accounts + get_connection_health. Each maps to a new /lc_gtm/* httpAction route in convex/http.ts (mirroring the ~30 existing /lc_gtm/* routes) that server-side instantiates ZernioClient with our sk_ key and the founder's connected accountIds — ALWAYS filtered by the founder's zernioProfileId (fail-closed cross-tenant isolation; ideally mint profile-scoped keys, scope=profiles).

CONNECT FLOW (browser, NOT the Fly agent): Convex actions getZernioConnectUrl(platform) -> GET /v1/connect/{platform}?profileId=X&redirect_url=OURS returns authUrl; the web app opens it; Zernio hosts the OAuth + account-picker UI; redirects back to a NEW public web/Convex callback route /lc_gtm/zernio_callback catching ?connected&accountId&profileId&username. We POST /v1/profiles once per founder at first connect and persist profile._id.

WEBHOOK HANDLER: new httpAction at /lc_gtm/zernio_webhook in convex/http.ts, modeled EXACTLY on the existing /telegram/webhook pairing. It reads request.text() (raw body) BEFORE JSON-parse, verifies X-Zernio-Signature via crypto.subtle HMAC (NOT Node crypto — Convex V8 has crypto.subtle, reuse the constantTimeEqual helper), dedupes the X-Zernio-Event-Id into a new idempotency store, returns 2xx within the 5s deadline, then ctx.scheduler.runAfter(0,...) an internalAction that maps event->prompt and POSTs to https://<flyApp>.fly.dev/hooks/agent (reuse runAgentTurn from phase2Trigger.fireBootPhase2Webhook). Do NOT call Fly inline (cold machine blows the 5s window). Register the webhook once at first-connect via POST /webhooks/create-webhook-settings, store webhook _id + secret on the gtmAgent.

CONNECT-STATUS GATES AUTO-POST: post_to_channel and the calendar publisher consult, fail-closed and server-side, (a) planFeaturesGtm (NOT yet built — $49 Base vs $99 Pro; auto-post + connected-channel count is the cost boundary to tier) and (b) the founder's live connection health (/v1/accounts/health: canPost + tokenValid). No connect = no post. Ban-risk channels (Reddit/TikTok) gated to manual/confirm even when connected.

SCHEMA (additive, GTM-keyed): do NOT reuse businesses-keyed zernioConnections/mayaTaskQueue. Per the documented TypeScript DataModel-ceiling constraint on gtmAgents (the slideshow library is a JSON string for exactly this reason), encode Zernio connection state as JSON-string fields on the gtmAgent row — zernioProfileId (string), zernioWebhookId + encrypted zernioWebhookSecret, and a connectedAccounts JSON array [{accountId, platform, username, isActive, needsReconnect}] — rather than adding new tables that would regress db.get() narrowing project-wide. The webhook idempotency store can reuse the existing webhookEvents pattern (by_provider_and_event_id) keyed by provider='zernio'.

## Costs / unit economics
Pricing model is pay-per-CONNECTED-ACCOUNT, billed to OUR app key and aggregated across all users: first 2 accounts free (per profile/social-set), then ~$6/acct for 3-10, $3 for 11-100, $1 for 101+. Per Maya user: a 3-channel founder = ~$6/mo (2 free + 1), a 6-channel founder = ~$24/mo (2 free + 4 @ $6). ON TOP of that, X is metered pass-through with zero markup: $0.005/analytics read, $0.010/user read, $0.015/post or DM, and critically $0.20/post-WITH-URL — and Maya's entire job is posting the founder's app link, so nearly every X post hits the $0.20 tier. WhatsApp adds ~$2/mo/number.

Unit-economics impact: against a $49 Base tier, a 6-channel user at ~$24 Zernio + X metering is ~50%+ gross-margin erosion BEFORE LLM/video COGS — so Base CANNOT include auto-post or deep reads. Conclusion for planFeaturesGtm (not yet built): $49 Base = research + drafts + deep-link calendar + wrapped-link attribution ONLY (no Zernio connect). $99 Pro = \"Maya posts for you\" + reads + monitoring, with the NUMBER OF CONNECTED/AUTO-POSTED CHANNELS as the metered cost boundary (e.g. cap at 3-4 included channels, additional channels as an add-on or Studio). Absorb the 2-free + 1-2 paid channels on Pro; never offer unlimited channel auto-post on a sub-$99 tier. NEVER gate ban-safety or attribution behind cost — those are the anti-churn moat. The connect step is the moment billing starts, which is exactly why it must be optional and Pro-tier-framed, not default-on.

## Full research findings

### WRITE / PUBLISHING capabilities (Zernio POST /posts)
Zernio's write layer is a single endpoint — POST /v1/posts — that publishes one piece of content to many platforms at once. The same call handles publish-now (publishNow: true), scheduled (scheduledFor + timezone), and draft (omit both). Media is referenced by URL via a presign-and-PUT upload flow (POST /v1/media/presign → PUT to uploadUrl → reference publicUrl in mediaItems). Content type per platform is driven by contentType + per-platform overrides in customContent/platformOptions. Critically for Maya's "we post for you" promise: Zernio holds the platform app-approvals itself, so our single app-level ZERNIO_API_KEY can auto-publish to all 15 platforms with no per-platform developer review (this is the thing that was blocking us — TikTok/IG/YouTube normally require multi-week app approval to auto-post). Every major channel Maya targets — X, Reddit, LinkedIn, Instagram, TikTok, YouTube, Threads, Facebook, Pinterest — is genuinely auto-postable through one API key. The real per-platform constraints are content shape (text-only vs media-required), required fields (subreddit/flair, board, TikTok consent flags), and rate limits — not approval walls.

**Capabilities:**
- Single endpoint POST /v1/posts does everything: 'Create and optionally publish a post.' Required fields are only `content` (post text, optional if media attached) and `platforms` (array of {platform, accountId}). 'You can post to multiple platforms at once. Just add more entries to the platforms array.'
- Three publish modes from the same call: publish-now (`publishNow: true`), scheduled (`scheduledFor` ISO timestamp + `timezone`), and DRAFT (omit both scheduling params / publishNow:false). Response statuses: draft / scheduled / published / failed / partial. Immediate posts return `platformPostUrl` per platform.
- Per-platform content overrides via `customContent` / `platformOptions` / `platformSpecific` so one call can shorten text for Threads (500 char) while keeping long text for LinkedIn (3,000). Also supports `firstComment` (auto-posted reply, used for links) and `threadItems` (X/Threads multi-post sequences, threadItems[0] = root).
- Media = upload-then-reference via presigned URL: POST /v1/media/presign with {fileName, fileType} returns {uploadUrl, publicUrl, expires}; PUT the bytes to uploadUrl (no auth); then reference in posts as `mediaItems: [{url: publicUrl, type: 'image'|'video'}]`. Direct CDN URLs required — Google Drive/Dropbox/OneDrive links do NOT work.
- X/Twitter: text tweets, up to 4 images, 1 video, 1 GIF, polls, AND native threads (threadItems). 280 chars free / 25,000 Premium. URLs always count as 23 chars. Reply (`replyToTweetId`) and quote (`quoteTweetId`) supported. Fully auto-postable.
- Reddit: self/text posts (40,000 char body), link posts, single image, gallery, native video. Title max 300 chars, cannot be edited after posting; subreddit required (without r/ prefix, or account default); many subreddits require flair (fetch via flairs endpoint). Zernio auto-retries: converts link→text if subreddit is text-only, applies first available flair if missing. Fully auto-postable.
- LinkedIn: text (3,000 chars), single/multi-image (up to 20, 8MB each), 1 video (5GB), and document/PDF carousels (1 per post, 100MB, title required). Cannot mix media types. Posts to personal profiles AND company pages (pages get fuller analytics/comments). Fully auto-postable.
- Instagram: feed image/video, carousel (up to 10 mixed items), Reels (`contentType: 'reels'`), Stories (`contentType: 'story'`). Caption 2,200 chars. Media required (no text-only). Fully auto-postable via Zernio.
- TikTok: video posts (3s–10min, up to 4GB) and photo carousels (up to 35 images). Caption 2,200; carousel title 90 chars. Media required. Auto-postable through Zernio with no app-approval wait.
- YouTube: regular videos and Shorts (auto-detected by duration<3min + 9:16). title (max 100), visibility (public/private/unlisted), categoryId (default 22), madeForKids, containsSyntheticMedia. Custom thumbnails NOT supported for Shorts via API. Fully auto-postable.
- Threads (text 500 / image / video 1GB,5min / carousel 10 / thread sequences), Facebook (text 63,206 / multi-image 10 / video / Reels / Stories / link carousels; Pages only), Pinterest (image/video pins, boardId effectively required, title 100, HTTPS destination link, no carousels) all auto-postable.
- Auto-postable WITHOUT per-platform developer approval: 'with Zernio, there's no approval process; get your API key and start posting immediately.' Zernio wraps TikTok's Content Posting API (normally a 2-6 week app review) and the IG Graph API behind one endpoint.

### read-analytics
A Zernio-connected account gives Maya a genuinely comprehensive read layer, far beyond our current wrapped-link clicks + ScrapeCreators voice scrape. THREE distinct read surfaces: (1) POST ANALYTICS — per-post and aggregated engagement metrics (impressions/reach/likes/comments/shares/saves/clicks/views/engagementRate) via GET /v1/analytics, plus account-level insights, audience demographics (age/gender/city/country), and follower growth history per platform; (2) INBOX MONITORING — unified DMs/conversations, comments on the user's posts, and reviews aggregated across all connected accounts in one call, each readable AND replyable; (3) DERIVED ANALYTICS — best-time-to-post, content-decay, posting-frequency-vs-engagement, daily aggregates. Critical caveats: the read layer fires only on accounts the USER has OAuth-connected (our onboarding does NOT connect accounts today — it only ScrapeCreators-reads handles), it requires the Analytics add-on (post/follower analytics) and Inbox add-on (DMs/comments/reviews) — both bundled on usage-based plans but gated on legacy plans (402/403), data is materially delayed (post analytics cached 60 min, IG up to 48h, YouTube 2-3 days, follower counts daily), and platform coverage is very uneven — IG/YouTube have the deepest reads, X is paid-and-degraded (encrypted X Chat DMs unreadable, per-call metered pass-through, DM writes need $5k/mo X Pro tier), and TikTok/LinkedIn/Reddit each have specific limits.

**Capabilities:**

Works on posts published via Zernio (`source=late`) OR external posts synced from the platform (`source=external`) — so it can read posts the founder published manually, not only ones Maya posted.

Sortable by engagement/impressions/reach/likes/comments/shares/saves/clicks/views; fromDate defaults 90d ago, max range 366 days.

### connect-auth-ux — Zernio AUTH + the user connect flow (OAuth-as-a-service)
Zernio's connect flow is a clean two-tier model that fits Maya well. App-level auth is a single ZERNIO_API_KEY (sk_ Bearer; we already have it). Each FOUNDER connects their own social accounts through Zernio's HOSTED OAuth flow: we call GET /v1/connect/{platform}?profileId=X&redirect_url=OURS, get back an authUrl, send the founder to it (new tab / popup), Zernio hosts the entire OAuth + account-selection UI (Facebook page picker, LinkedIn org picker, etc.), then redirects back to our redirect_url with ?connected={platform}&profileId=X&accountId=Y&username=Z. We never build OAuth UI, never store platform tokens, never handle client secrets — Zernio does all of it. The data model is two levels: a "profile" is a container/brand (we create one profile per Maya/founder via POST /v1/profiles and store its _id on the gtmAgent), and "accounts" are the connected social accounts that live under a profile. We associate a connected account with our user by (a) creating a dedicated Zernio profile per founder and (b) reading the accountId/profileId off the redirect callback (or polling GET /v1/accounts?profileId=X). Connection status/health is first-class: GET /v1/accounts/health returns per-account tokenValid/canPost/canFetchAnalytics/needsReconnect; webhooks account.connected and account.disconnected fire on connect / token-expiry. Disconnect = DELETE /v1/accounts/{accountId}. RECOMMENDATION: do NOT block onboarding on it — keep capturing handles as today (read-only voice extraction), and add an OPTIONAL "Connect so Maya can post for you" step that reuses the existing Telegram connectBot() status-state UI pattern, plus a persistent Settings/Profile "Connected accounts" panel driven by /v1/accounts/health.

**Capabilities:**
- App auth is one shared API key: bearerAuth = 'Authorization: Bearer sk_<64 hex>' (we already have ZERNIO_API_KEY). Keys are SHA-256 hashed server-side, shown once at creation.
- Per-user account connection is OAuth-AS-A-SERVICE, HOSTED by Zernio (NOT embed/iframe). Quote: 'Standard flow: Zernio hosts the selection UI, then redirects to your redirect_url.' We just redirect the browser to the returned authUrl.
- GET /v1/connect/{platform} returns { authUrl, state }. We pass our own redirect_url; on success Zernio appends '?connected={platform}&profileId=X&accountId=Y&username=Z' so we learn exactly which account connected without a second call. Quote: 'Standard mode appends ?connected={platform}&profileId=X&accountId=Y&username=Z.'
- Profiles vs Accounts: 'Profiles - Containers that group social accounts together (think brands or projects)'; 'Accounts - Your connected social media accounts, belonging to profiles.' We create ONE profile per founder (POST /v1/profiles {name}) and store profile._id on the gtmAgent row.
- Associating connected account -> our user works two ways: (1) the callback redirect carries accountId+profileId, and (2) GET /v1/accounts?profileId=X lists that founder's accounts. SocialAccount has _id, platform, profileId, username, displayName, profilePicture, profileUrl, isActive.
- Connection STATUS is observable three ways: SocialAccount.isActive (boolean), GET /v1/accounts/health (per-account status healthy|warning|error + tokenValid, tokenExpiresAt, canPost, canFetchAnalytics, needsReconnect, issues[]), and webhooks account.connected / account.disconnected.
- Disconnect: DELETE /v1/accounts/{accountId} -> 'Account disconnected successfully'. Move between profiles: PATCH /v1/accounts/{accountId} {profileId}. Rename: PUT /v1/accounts/{accountId} {displayName, username}.
- Zernio handles the multi-step platform pickers itself in hosted mode (Facebook page select, GBP location select, LinkedIn org select, Pinterest board select, WhatsApp number select, Telegram bot-code flow) — we get a single clean callback. A 'headless=true' mode exists to build our OWN selection UI, but it requires us to implement the per-platform selection endpoints (X-Connect-Token / pendingDataToken) — NOT worth it for v1.
- API keys can be SCOPED: ApiKey.scope = full | profiles (+ profileIds[]) and permission = read-write | read. This means we can mint per-founder profile-scoped keys for stronger cross-tenant isolation if desired.

**Endpoints:**
- POST /v1/profiles { name, description?, color? } -> 201 { profile: { _id, userId, name, isDefault, ... } } — create one profile per founder
- GET /v1/profiles?includeOverLimit= -> { profiles: [{ _id, name, color, isDefault, isOverLimit? }] }
- GET /v1/profiles/{profileId}, PUT /v1/profiles/{profileId}, DELETE /v1/profiles/{profileId} (DELETE 400s if it still has connected accounts)
- GET /v1/connect/{platform}?profileId={id}&redirect_url={ours}&headless=false -> 200 { authUrl, state }. platform enum: facebook,instagram,linkedin,twitter,tiktok,youtube,threads,reddit,pinterest,bluesky,googlebusiness,telegram,snapchat,discord,whatsapp
- POST /v1/connect/{platform} { code, state, profileId } -> exchange OAuth code for token (only needed for headless/custom-callback flows; hosted mode does this internally)
- GET /v1/accounts?profileId={id}&platform= -> { accounts: [SocialAccount], hasAnalyticsAccess } — SocialAccount: { _id, platform, profileId, username, displayName, profilePicture, profileUrl, isActive }
- GET /v1/accounts/health?profileId=&platform=&status= -> { summary: {total,healthy,warning,error,needsReconnect}, accounts: [{ accountId, platform, username, status, canPost, canFetchAnalytics, tokenValid, tokenExpiresAt, needsReconnect, issues[] }] }
- DELETE /v1/accounts/{accountId} -> disconnect; PUT /v1/accounts/{accountId} {displayName,username}; PATCH /v1/accounts/{accountId} {profileId} move to another profile
- Webhooks: account.connected, account.disconnected (payload includes accountId, profileId, platform, username, disconnectionType=intentional|unintentional, reason). account.disconnected fires on token expiry too.
- Security schemes: bearerAuth (X-API key as Bearer) for all of the above; connectToken (header X-Connect-Token, 15-min TTL) only for headless per-platform selection calls — not needed in hosted mode.
- Special non-OAuth connects (if we ever want them): POST /v1/connect/bluesky/credentials (handle + app password), POST /v1/connect/whatsapp/credentials, GET/PATCH /v1/connect/telegram (15-min access code, add bot as admin then poll).

**Gotchas:**
- The hosted flow is a full-page/redirect OAuth, NOT an embeddable iframe/SDK widget. So it must open in a new tab or popup and round-trip back to a redirect_url we control — we need a real server-rendered/Convex HTTP callback route (e.g. /lc_gtm/zernio_callback) to catch ?connected=...&accountId=... Our deployed agent is OpenClaw on Fly and the web app is Next.js/Convex; the callback must land on the WEB app (it has the browser session), not the Fly agent.
- Profile per founder is on US to create and store. Zernio gives every account a default profile, but for multi-tenant isolation we should explicitly POST /v1/profiles per founder and persist profile._id on the gtmAgent. Today there is NO profileId/zernioProfileId column in convex/schema.ts — schema work required.
- Cross-tenant risk: a single shared full-scope API key sees ALL profiles/accounts across ALL founders. Our /lc_gtm plugin tools and any GET /v1/accounts call MUST always filter by the founder's profileId, and ideally mint profile-scoped keys (scope=profiles). This is exactly the kind of fail-closed isolation CLAUDE.md mandates.

### webhooks-realtime

ADS/LEADS: lead.received (Meta Lead Gen form submit), ad.status_changed. WHATSAPP PROVISIONING: whatsapp.number.activated, whatsapp.number.declined, whatsapp.number.verification_required. TESTING: webhook.test.
- Universal payload fields on every event: `id` (UUID string, for dedupe), `event` (event-type string), `timestamp` (ISO-8601). Event-specific top-level objects: post events carry a `post` object; message events carry `message` + `conversation` + `account` + optional `metadata`; account events carry `account` (+ `sync` object with status/backfill/error codes like token_invalid, permission_denied, no_ad_accounts for ads sync); ad.status_changed carries `adObject` (level CAMPAIGN|AD_SET|AD, platformAdAccountId), `status.raw` (ACTIVE|PAUSED|PENDING_REVIEW|WITH_ISSUES), and `error` (code/summary/message).
- HMAC-SHA256 signing: signature sent in `X-Zernio-Signature` (lowercase hex digest of the raw request body keyed with the webhook secret). Legacy aliases for backward compat: `X-Late-Signature` (signature) and `X-Late-Event-Id` (event id). Canonical event id header: `X-Zernio-Event-Id`. Secret is configured per-webhook at create time. Docs explicitly say: 'Reject unsigned or mismatched requests.'
- At-least-once delivery — 'the same event may arrive more than once if a previous attempt's response was lost.' Success = endpoint returns 2xx within 5 seconds. Idempotency pattern the docs recommend: insert payload.id (or X-Zernio-Event-Id) into a unique-indexed table/cache before processing, skip on conflict.
- Subscription management endpoints: POST /webhooks/create-webhook-settings (set url, events to monitor, secret for HMAC), POST /webhooks/update-webhook-settings (modify subscriptions), POST /webhooks/test-webhook (sends a webhook.test payload to validate the endpoint). GET /v1/webhooks/settings lists configured webhooks; list response fields include `_id`, `name`, `url`, `events`, `isActive`, `lastFiredAt`, `failureCount`.
- Platform-specific real-time notes: Instagram/Facebook support message edit/delete webhooks; WhatsApp includes failure codes + delivery/read tracking; Telegram reaction webhooks require bot admin permission; Meta Ads status changes fan out per linked ad account (expect multiple deliveries); Google Business review webhooks are delivered real-time via Cloud Pub/Sub.
- Our codebase already has the full precedent for this: convex/gtmMaya/telegramWebhook.ts is a signature-verifying httpAction (constant-time secret compare, dedupe, fast 2xx) mounted in convex/http.ts at /telegram/webhook. The agent-wake mechanism exists too: phase2Trigger.fireBootPhase2Webhook POSTs a prompt to https://<flyApp>.fly.dev/hooks (runAgentTurn) with { message, deliver:true, channel:'telegram', to:<chatId>, thinking }.

**Endpoints:**
- POST https://zernio.com/api/v1/webhooks/create-webhook-settings — body (per docs): name, url, events[] (array of event-type strings), secret (HMAC key); enable selectively. Auth: ZERNIO_API_KEY (sk_).
- POST https://zernio.com/api/v1/webhooks/update-webhook-settings — modify url / events[] / secret on an existing webhook.
- POST https://zernio.com/api/v1/webhooks/test-webhook — fires a webhook.test event to the configured URL to validate delivery.
- GET https://zernio.com/api/v1/webhooks/settings — list configured webhooks; returns _id, name, url, events, isActive, lastFiredAt, failureCount.
- Inbound (their POST → us): they POST event JSON to OUR Convex httpAction URL with headers X-Zernio-Signature (HMAC-SHA256 hex of raw body), X-Zernio-Event-Id (UUID), and legacy X-Late-Signature / X-Late-Event-Id. Our new endpoint would be e.g. POST /lc_gtm/zernio_webhook (mounted in convex/http.ts alongside /telegram/webhook).
- Agent-wake (us → OpenClaw): POST https://<flyAppName>.fly.dev/hooks/agent with { message, deliver, channel, to, thinking } — the existing runAgentTurn contract used by fireBootPhase2Webhook in convex/gtmMaya/phase2Trigger.ts.

**Gotchas:**
- Event-count + retry/auto-disable semantics CONFLICT across doc versions — resolve before relying on them. The current reference page (docs.zernio.com/core/webhooks) says 'max 10 webhooks per user' and 'webhooks automatically disabled after 10 consecutive delivery failures.' The /webhooks overview page says '7 retry attempts then dead-letter queue, webhooks NEVER auto-disabled.' The context brief says 29 events; the overview enumerates 28. Confirm the live numbers via test-webhook + GET /webhooks/settings before building dedupe/alerting against assumptions.
- 5-second 2xx deadline is tight for a Convex httpAction that also wants to wake a Fly agent. MUST split: httpAction verifies signature + dedupes + persists the event, returns 2xx immediately, and schedules a separate internalAction (ctx.scheduler.runAfter(0, ...)) to POST the Fly /hooks/agent wake. Do NOT call the Fly machine inline — a cold/slow Fly machine would blow the 5s window and trigger retries.
- HMAC must use Web Crypto, not Node crypto. Convex runtime has crypto.subtle (we use crypto.subtle.digest('SHA-256') in mediaAssets.ts and 3 other files) but NOT Node's crypto.createHmac shown in Zernio's JS sample. Verification = crypto.subtle.importKey('raw', secretBytes, {name:'HMAC',hash:'SHA-256'}, false, ['sign']) then sign the raw body and compare hex constant-time (reuse the constantTimeEqual helper already in telegramWebhook.ts). Must read request.text() (raw body) BEFORE any JSON parse — re-serialized JSON will not match the signature.
- At-least-once → idempotency is mandatory. Need a new gtmZernioWebhookEvents table with a unique index on the event id; insert-before-process, skip on conflict. Without it, comment.received duplicates = Maya drafts the same reply twice, post.published duplicates = double-counted analytics tracking.
- Cost/architecture coupling: webhooks only fire for accounts the founder has CONNECTED to Zernio. Today our onboarding only captures handles and READS them via ScrapeCreators — the user never connects a write/analytics account. So this whole feature is gated on first shipping the OAuth-connect flow (GET /connect/{platform}) and paying per-connected-account (~$6/acct 3-10). No connect = no webhooks = no real-time loop.
- Meta Ads ad.status_changed fans out per linked ad account (duplicate deliveries by design); Telegram reactions need bot-admin; Google Business reviews ride Pub/Sub. Per-platform availability is uneven — don't assume a uniform event surface across all 15 platforms.
- Webhooks are 'notifications, not an authoritative sync source' (docs). For analytics that matter (attribution), use post.published only as a TRIGGER to then pull GET /v1/analytics for that post — don't treat the webhook payload as the source of truth for metrics.
